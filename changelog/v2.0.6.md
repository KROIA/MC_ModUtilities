# 2.0.6 — In Development

Minecraft 1.21.1 | Fabric, NeoForge

## API

| Tag | Change |
|---:|---|
| ![feature] | <details><summary>New GUI API: screens can hide JEI's overlay or specific overlay buttons while open</summary><br>Screens extending `GuiScreen` / `GuiContainerScreen` can now opt into hiding JEI's ingredient list + bookmark overlays (`setHideJeiOverlay(true)`) or only named overlay buttons like the config gear / bookmark toggle / lookup-history toggle (`setHideJeiButtons(String...)`) while they are open. Set it once in the subclass constructor and the base class handles hide-on-open, hide-on-resize (idempotent), and restore-on-close automatically.<br><br>Safe when JEI is absent — the broker no-ops. Screens that don't opt in are unchanged. Adds JEI as a soft dev-runtime dependency on Fabric and NeoForge so the platform transformer can resolve the reflected JEI types at launch.</details> |
| ![bugfix] | <details><summary>`ServerPlayerUtilities.addToPlayerInventory` merged stacks by raw item type, ignoring data components</summary><br>**Root cause:** The merge-target predicate was `currentStack.is(stackCpy.getItem())` — plain item-type equality. Two stacks of the same item with different data components (enchantments, damage, custom name, TFC `tfc:food` decay state, etc.) were merged into one stack, silently rewriting the inserted items' state to match the existing stack. Vanilla `Inventory.add` uses `ItemStack.isSameItemSameComponents` and mods (e.g. TerraFirmaCraft) mixin that method to define stateful merge semantics — component-blind merging bypassed all of that.<br><br>**Fix:** merge predicate now `ItemStack.isSameItemSameComponents(currentStack, stackCpy)` — matches vanilla contract and respects mod hooks that gate merging on component state. Count / max-size math and the mutation contract on the input `stack` (dependent mods rely on `stack.setCount(remainingAmount)` for overflow handling) are unchanged.</details> |

## UI / UX

| Tag | Change |
|---:|---|
| ![bugfix] | <details><summary>`TextBox` crashed with `StringIndexOutOfBoundsException` on Backspace/Delete when a prior selection had gone stale</summary><br>**Root cause:** `TextBox.setText(String)` clamped the cursor to the new text length but never reset `selectionCursonIdxStart` / `selectionCursonIdxEnd`. Any external caller that shortened the text while a selection was active (e.g. an `onTextChanged` callback in a dependent mod) left the selection pointing past the current text length. The next Backspace / Delete / character-insert executed `text.substring(0, staleStart) + text.substring(staleEnd)` and threw `Range [3, 0) out of bounds for length 0`, crashing the client to the error screen.<br><br>**Fix:** `setText` now clears the selection. A new `hasValidSelection()` helper bounds-checks both indices against the current `text.length()`; all seven selection-slice sites (Ctrl+C, Ctrl+X, paste-with-regex, paste-mutate, Backspace, Delete, char-typed) route through it and order-normalize the selection into `s = min(start, end)` / `e = max(start, end)` before slicing — as a side benefit, this also fixes latent breakage on reversed (shift+left) selections.</details> |
